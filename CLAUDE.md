# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository purpose

This repository is for authoring and collecting agent skills focused on research workflows, industrial R&D, paper writing, PhD applications, language test preparation, presentation/deck building, and implementation-heavy coding work. Skills should help agents support research ideation, literature grounding, industry problem framing, solution design, pilot evaluation, implementation, reproducibility, paper writing, reviewer response, artifact release, research-oriented applications, IELTS preparation, slide/deck production, and coding support.

Coding-support skills are allowed only when they encode something a capable agent does *not* already do by default; generic craft guidance (style, testing patterns, standard debugging) is explicitly out of scope and was removed from this repo. Generic README, architecture, slide, or meta-discovery skills should not be added unless they directly support research, industrial R&D, paper production, PhD applications, language test preparation, presentation/deck building, or coding-heavy research work.

## Structure

- `skills/` contains individual skills. Each skill should live in its own directory and include a `SKILL.md` file.
- `DESIGN-PHILOSOPHY.md` records the repo's durable skill-design rationale and supporting references. When adding, removing, or materially changing skill-family philosophy, learning/audit protocols, role boundaries, or evidence-backed design claims, update this file if the change affects the rationale.
- Skills are filed at `skills/<category>/<skill>/SKILL.md` — **at most two levels under `skills/`**. This is not cosmetic: the skills CLI's default discovery stops at that depth, so a skill nested deeper is invisible to anyone installing without `--full-depth`. Do not create sub-categories inside a category; group siblings with a name prefix (`theory-*`, `apply-*`, `banking-*`, `flow-*`) instead.
- `skills/init-workspace/` sits at the top level *deliberately*, as the entrypoint skill for starting any new project. Top-level placement is reserved for that role; everything else belongs in a category.
- `skills/research-discovery/` contains early-stage research framing skills, plus `gap-finder` (mining others' papers for one's own research gaps — discovery work, not claim-checking; it also owns the weekly lemma-autopsy habit: weaken one hypothesis, predict the first failed proof line, construct the smallest witness, and only then compare with the authors' discussion). It also holds `cross-domain-analogy-finder`, a high-variance foraging skill that finds a concept's structural twin in a distant field — either to borrow a portable solution (offense) or to check whether an idea already exists under another name (defense) — gated by a four-way classifier (identical / portable / twin-with-a-delta / surface-only) and an import-a-result test; it grounds prior-art claims through `literature-triangulation` and hands a twin's residual mismatch to `gap-finder`. It is for distant-field structural transfer, not near-field paper search or area survey (both `literature-triangulation`) or stress-testing one chosen idea (`research-idea-stress-test`). The directory also holds `gap-motivation-builder`, the Socratic bridge between finding a gap and proposing a solution: it takes one gap (from `gap-finder` or anywhere else) and interrogates the five-link motivation chain (consequence → beneficiary → blocker → timeliness → payoff), refuses "understudied" as motivation (gap-spotting vs problematization), runs the why-hasn't-this-been-done trichotomy (trivial / done under another name / genuine blocker), and converges on a verdict (MOTIVATED / CONDITIONALLY MOTIVATED / WEAK / UNMOTIVATED / NOT A GAP) plus solution desiderata — requirements any future method must satisfy, each traced to a chain link, including at least one anti-desideratum — while never proposing the method itself. Keep the pipeline boundaries: `gap-finder` finds gaps, `gap-motivation-builder` motivates one and derives desiderata, `research-idea-stress-test` attacks the chosen solution direction, `paper-idea-and-scope-brainstormer` scopes the paper, and `abstract-and-intro-writer` turns a finished motivation into prose.
- `skills/research-evidence/` contains literature mapping, Related Work writing, standalone survey/tutorial/perspective paper writing, and citation verification skills. Keep the boundary clear: `related-work-writer` is for Related Work sections inside original research papers, while `survey-paper-writer` is for papers whose main contribution is the synthesis/taxonomy/tutorial/roadmap itself.
- `skills/research-experimentation/` contains experiment design, benchmark/baseline selection, statistical testing, and evaluation skills. `experiment-design` covers both halves of the empirical loop: designing the minimal decision-relevant experiment *and* diagnosing a run that already went wrong (symptom classification → data-path audit → mechanism-wise tuning), plus scaling-curve fitting via its bundled `scripts/fit_scaling_law.py`. The former `deep-learning-experimentation/` sub-family (data-pipeline-auditor, training-run-forensics, hyperparameter-triage, experiment-trace-summarizer, representation-probe-designer, scaling-law-tracker) was folded into it — do not re-add those as separate skills; they were ~200-word restatements of default behavior.
- `skills/research-engineering/` contains implementation recipes for research experiments (PyTorch, JAX) plus `research-codebase` for the harness around a single paper's experiments. `research-codebase` is calibrated for users strong in mathematics who cannot code, whose goal is many experiments fast. It therefore **rejects** "add structure only when the pain justifies it" (that stance assumes someone who will notice the pain and can refactor) and instead fixes a four-stage contract up front: data (`generate`/`load`), a plain-dict `ALGORITHMS` registry, a plain-dict `METRICS` registry with **model-free** `metric(result, data)`, and a fixed store (`outputs/<run_id>/{config,metrics}.json` → `aggregate.py` → CSV + booktabs LaTeX). Load-bearing invariants: a one-round five-question intake in paper vocabulary that never blocks; algorithms return a **result dict** so no metric touches a fitted object (a metric reading `model.coef_` works on a custom class and crashes on a sklearn baseline — undebuggable for this audience), with an optional `"model"` escape hatch; a params-list runner with skip-if-done replacing one-`.sh`-per-run; machine-written provenance (argv, params, seed, git SHA); aggregation over **every** matching run (never max/top-N) with bootstrap CIs and no hardcoded seed count; train/test quantities as separate columns. `assets/project-template/` must **run end-to-end on toy data** — a template with `TODO` holes is unusable by a non-coder — verified by `python sanity_check.py && python run.py && python aggregate.py`. `references/evidence-base.md` carries only findings that change an instruction, with attributions and declines recorded there; notably Michelucci & Venturini's LOR/COS overfitting scores are **not adopted** (COS is non-identifiable and LOR's sign convention inverts between error- and accuracy-type metrics), and overfitting diagnosis belongs to `experiment-design`. It also holds `paper-to-code`, which reproduces a paper's method in minimal single-file PyTorch when no official code exists, to check whether the method works as claimed — one falsifiable claim, an assumptions ledger for underspecified details (backed by `references/underspecified-defaults.md`), staged verification gates (mechanics → overfit tiny batch → directional method-vs-baseline test), and an explicit works/doesn't/inconclusive verdict. It is for sanity reproduction, not for designing your own training setup (`pytorch-training-recipe`/`jax-training-recipe`) or auditing a released artifact (`reproducibility-audit`).
- `skills/research-reasoning/` contains theorem, claim, proof, and theory-heavy skills (`gap-finder` now lives in `research-discovery`). Keep the two claim-checkers distinct: `argument-audit` is the domain-general, interactive/Socratic "does the stated evidence actually establish this claim" checker (math, essay, or everyday argument) that walks the user to the weak link one question at a time and converges to a validity verdict + smallest fix — whereas `theorem-and-claim-audit` is the direct, report-style audit specialized to formal math/ML claims (verdict handed over, not Socratic), and it now also owns step-by-step derivation checking (the former theory-derivation-auditor, merged in: name the rule justifying each step, flag silent assumptions, mark the *first* invalid step). Route general "is this reasoning valid" questions to `argument-audit`, heavily mathematical/empirical paper claims wanting a written audit to `theorem-and-claim-audit`, and external "does the cited source actually say this" to `citation-auditor`.
- `skills/learning-and-metacognition/` contains the teaching and metacognitive role family. `professor-mentor-technical-teaching` teaches fresh material; `concept-exercise-generator` builds graded verification practice; `knowledge-debt-audit` audits ownership of AI-assisted load-bearing steps and schedules variable-cue re-probes after repayment; `naive-student` lets the user repay or verify understanding by teaching an honest novice whose confusion must be earned from the actual explanation; `whiteboard-peer` co-solves the unfinished middle with committed partial attempts and real disagreement but never takes over the full solution; and `professor-critic` grades a finished artifact against a named reader and acceptance bar with a verdict-first FATAL/MAJOR/MINOR teardown. Keep the stage boundaries intact: novice playback is not teaching, whiteboard collaboration is not finished-artifact grading, and ownership audit is not exercise generation. Use `peer-review-writer` when the user reviews someone else's paper and `submission-readiness-audit` for a whole-paper author checklist.
- `skills/research-communication/` contains paper narrative, section writing, discussion-report synthesis, and talk-planning skills — each scoped to one artifact (abstract, intro, method, figures, results prose, talk plan, research proposal). The whole-draft writing coach that used to live here (paper-writer) is now **stage 10 of `flow-paper-lifecycle`**, which owns the four writing sub-phases (10a story/skeleton, 10b drafting, 10c math-prose pass, 10d handoff) and their gates, and carries the five `references/writing-*.md` files. Route "draft/outline the whole paper" there; route narrow section work to the singletons here. The directory also holds `research-proposal-writer`, which drafts or refines *forward-looking* research proposals — plans for work not yet done, judged on plausibility and feasibility — in two modes sharing one skeleton: a multi-year PhD research proposal for a prospective supervisor/committee/fellowship, and a one-cycle next-paper pitch to the user's current advisor. It owns the proposal-specific document craft (promise questions and deliverables, never outcomes; methodology as argument not agenda; checkable milestones with named pivots; risk→fallback tables where every fallback still yields a contribution; ambition calibration per horizon; fit-as-dependency in PhD mode), grounded in a `references/proposal-sources.md` distillation (Heilmeier Catechism, SSRC, MIT Comm Lab, Peyton Jones, Ten Simple Rules) with volatile program details routed to "verify against the live call". Keep its boundaries: it is not the SOP essay (`apply-sop-writer`), not idea validation (`gap-motivation-builder` / `research-idea-stress-test`, which it routes to when the gap or direction is untested), not a named-reader verdict on a finished draft (`professor-critic`), and not defense slides (`deck-beamer-proposal-report`, strictly downstream).
- `skills/research-publishing/` contains reviewer-response, submission-readiness, venue-targeting, peer-review-writing, reproducibility-audit, and artifact-release skills. Note the author/reviewer split: `peer-review-writer` is for when the user is the REVIEWER of someone else's paper (claim–evidence map, weakness triage into fatal/fixable/minor, calibrated scores, meta-review and emergency-review modes, plus a PC-member / area-chair mode in `references/pc-member-guide.md` for bidding, COI, subreviewer management, and running discussion), while `reviewer-response-strategist` (author responding to reviews), `submission-readiness-audit` (author pre-submission), and `gap-finder` (mining a paper for one's own research) cover the author side; each disambiguates in its `description`.
- `skills/academic-career/` contains academic-career profile ingestion, PhD application writing, dossier scoring/eligibility evaluation, career support, and motivation skills. Note the deliberate split between `apply-package-auditor` (qualitative coherence/readiness audit, no scores) and `apply-dossier-evaluator` (reproducible 1–5 rubric across 11 dimensions, eligibility gate, and scholarship-program fit for VEF/DAAD/Fulbright/Erasmus/MSCA); each disambiguates against the other in its `description`. The directory also holds `apply-interview-prep`, which prepares the user for academic selection *interviews* (PhD admissions, funder committees, scholarship/embassy panels, MSc admissions, prospective-supervisor calls). Its load-bearing design decision is that the taxonomy is **who is across the table, not which country** — a funder's academic committee (A), a prospective supervisor (B), an administrative/embassy panel (C), and document-only processes with no interview at all (D) assess different things and reward different answers; region enters only as a self-presentation modifier. Organizing by region was rejected because "the working culture of Europe/Asia" is not describable without stereotyping, and because assessor type — not geography — is what actually predicts the preparation. **Type D must route out rather than manufacture interview prep** (SISGP, Italian DSU, IYT and most Erasmus Mundus consortia select on documents; the letter and references carry the load, so hand to `apply-sop-writer` / `apply-cv-builder` / `apply-recommendation-letter-strategist`). Its `references/structured-answer-evidence.md` is epistemically flagged per `DESIGN-PHILOSOPHY.md`: STAR's DDI-1974 provenance is *established*; Schmidt & Hunter's r=.51 structured-interview validity is *supported but measures interviewer predictive validity, not candidate admission odds* — never promote it to "STAR gets you admitted"; the Schmid Mast, Frauendorfer & Popovic (2011) self-promotion/modesty mismatch is *supported at population level only*, and Hofstede-derived national-trait scores are *contested and deliberately excluded*. All programme specifics (formats, weightings, age caps, degree levels, whether an interview exists) are routed to verify-against-the-live-call. Keep its boundaries: not the written essay (`apply-sop-writer`), not first contact before an interview exists (`apply-cold-email-drafter`), and it **delegates rehearsal grading to `professor-critic`** rather than issuing verdicts itself. **Cross-system (cultural) calibration** is applied across the family using the same discipline as `apply-interview-prep`: describe *what the receiving institution or call expects*, never what people from a country are like, and route every specific to the live call. It lands in four places, each with its own scoped file per the self-containment rule — `apply-cold-email-drafter/references/address-and-formality.md` (title and register conventions; take the recipient's title from their institutional page, never infer it from a name, and let their reply signature override the convention), `apply-cv-builder/references/cv-format-and-required-documents.md` (the call's required-documents list governs; Europass is genuinely required only for EU-funded calls and Italian *bandi* asking for *formato europeo*; grades stay on their native scale), `apply-sop-writer/references/statement-conventions-by-system.md` (the prompt defines the document, not its name; named-project vs department-first applications differ structurally), and a supervisor-first vs department-first paragraph in `apply-program-fit-mapper` that decides the shortlisting strategy. The family's adaptation model is **Applicant Evidence + Target Evidence + Selection/Funding Regime → Narrative Strategy** — the third term is deliberately a *published selection regime*, never a "regional cultural prior," because a funder's criteria are checkable and a nation's character is not. Its invariant is **facts fixed; weights vary**: adapting across targets changes salience, order, depth, and which published criterion evidence is framed against, never what the applicant did. Two anti-patterns are hard rules carried in `apply-sop-writer` and `apply-cold-email-drafter`: the **cultural-praise anti-pattern** (never show fit by praising national characteristics — "I admire Germany's precision" is evidence of nothing; test by asking whether the sentence would survive being moved to another country) and the **identity-mutation anti-pattern** (seven targets are not seven identities). A country enters the reasoning only where it produces a **documented institutional mechanism**, and a geopolitical fact licenses an emphasis only via the falsifiable chain *geopolitical objective → programme objective → published selection criterion* — Australia Awards passes it, "China emphasises self-reliance therefore write about self-reliance" does not. Beneath the country layer sits a **scholarship-regime layer**, because two schemes from the same national agency can demand opposite narratives (DAAD's main study/research lines want academic trajectory; DAAD **EPOS** is a development instrument requiring ~two years' professional experience and assessing capacity to initiate change). The family therefore encodes **seven genres** (academic-excellence, development/change, leadership/influence, industry/professional, research-cooperation, consortium/mobility, diplomatic/bilateral), **four application regimes** — supervisor-first (France, French-speaking Belgium), vacancy-first (Sweden and Norway, where doctoral candidates are *employees* and positions are advertised jobs), call/competition-first (Italian *bandi*), and department-first (typical US) — and an **extraction method** (identify application regime → identify funding regime → extract published criteria → reweight evidence → note hard constraints), with funding treated as an axis separate from admission because nominated schemes and sending partners introduce a second selector. A deliberate scope decision: **encode genres, regimes, and the method — never a scholarship catalogue.** Per-cycle specifics (GPA cutoffs, nomination quotas, years-of-experience minimums, eligible-country lists) were declined because they rot and are closer to a user's personal application data than to reusable skill content; three verified worked contrasts (DAAD vs EPOS, Master Mind vs VLIR-UOS, Swedish PhD vacancy vs SI) carry the pattern instead. The targeting-side copy lives in `apply-program-fit-mapper/references/application-regimes.md` (what a shortlist entry *is* per regime); the narrative-side copy in `apply-sop-writer`. Verified regime facts encoded across the family: France's doctoral structure requires a thesis topic and supervisor before enrolment with doctoral-school acceptance (**not** generalizable to "always contact a supervisor first"); Australia Awards is a development instrument with a return-home and two-years-outside-Australia condition carrying full-cost debt liability, structurally distinct from university-administered RTP; HKPFS publishes four yardsticks (academic excellence as prime, research ability/potential, communication/interpersonal, leadership); Tsinghua requires a research plan *in addition to* the personal statement; NSF GRFP's Intellectual Merit/Broader Impacts is **fellowship-specific and restricted to US citizens/nationals/permanent residents**, not evidence about US admissions generally. A TIGP "contact faculty first" rule was investigated and **declined** as unverified — do not re-add it. Two further guardrails are load-bearing and were reached deliberately: **do not assert that any country "expects a photo/date of birth" on an academic CV** — that is an industry-résumé convention, varies by document type and year, and asserting it pushes discriminatory personal data into applications that never asked for it; and the SOP file's **register claims are explicitly flagged as weakly sourced folklore** rather than stated as national rules. `apply-dossier-evaluator` carries the matching scoring guard: score the evidence, not the packaging — a fixable convention mismatch is a *highest-leverage fix*, never a reduced dimension score, and no score moves on nationality, first language, or home-institution country (credential *recognition* belongs to the eligibility gate). `apply-dossier-evaluator` bakes in a strict volatility split — stable structural logic only, with deadlines/cutoffs/score-minimums/word-limits/funding routed to a "verify against the live official call" instruction rather than committed as authoritative, and faculty/lab fit fetched live per run (no cached professor file).
- `skills/research-workflows/` contains lightweight router/meta-skills that sequence the singleton research skills into a guided workflow with stage gates, delegating the actual work to the singletons rather than duplicating it: `flow-learn-new-topic` (breadth-first onboarding into an unfamiliar area), `flow-deep-understanding` (depth-first mastery of one paper/method/theorem), `flow-idea-to-proof` (raw idea → formal claim → proof design), `flow-paper-lifecycle` (idea → experiments → writing → submission → rebuttal → artifact release), and `flow-phd-application` (profile → CV → fit → SOP → recommenders → outreach → package audit → interview prep, plus a *conditional* route to `apply-dossier-evaluator` for graded scoring, cross-border eligibility, or scholarship-mission fit — situational, not a linear stage). Orchestrators decide *what next* and which sub-skill to call; they never re-teach what a singleton already does. `flow-learn-new-topic` and `flow-deep-understanding` additionally carry a **discussion mode** — an alternative *gate verifier*, not a new stage: instead of clearing a stage with a `concept-exercise-generator` checkpoint, the user explains that stage's material to a cast (STUDENT = `naive-student`, PEER = `whiteboard-peer`, MENTOR = `professor-mentor-technical-teaching`, MODERATOR = the flow file itself), and the resulting playback clears the gate. Its two load-bearing rules must stay word-identical in both copies: (1) the STUDENT may use only what was spoken aloud in the session and tags every accepted link `[USER]`/`[PEER]`/`[MENTOR]`, and (2) the gate passes only when the playback holds *and* every load-bearing link is `[USER]`-owned, with borrowed links routed to `knowledge-debt-audit`. `professor-critic` must never fire mid-discussion — it requires a finished artifact, named reader, and acceptance bar, which live thinking-stage work lacks. Do not factor this section into a shared file (self-containment rule) and do not promote it to a third `flow-*` skill: it was deliberately folded into the two flows because users reach for discussion *while already inside* one of them.
- `skills/industrial-rnd/` contains skills for ambiguous industry problem framing, publication-grounded solution design, practical pilot/evaluation planning, and the banking/fintech domain specializations (the `banking-*` prefix groups them; there is no `banking/` sub-directory).
- `skills/presentation/` contains slide/deck *building* skills that render an approved per-slide spec into an artifact: `deck-beamer-academic` (Beamer for seminar/conference/lecture talks), `deck-beamer-proposal-report` (Beamer for proposals and progress/final reports), and `deck-business-report` (PowerPoint/Canva industrial/executive reports). Each builder is self-contained: the shared slide-spec schema and format-independent design rules were dissolved out of the former deck-design-principles skill into a per-builder `references/slide-spec-and-design.md` copy, so no builder depends on a sibling. These are downstream of `research-talk-planner`, which plans a talk's narrative and pacing but does not produce slides.
- `skills/coding-support/` holds `prompting-claude-models` only — prompt/system-prompt/agent-scaffolding *design* for Claude-backed features (LLM-as-judge, RAG, extraction, multi-step agents), deliberately split into a durable technique layer in `SKILL.md` and a volatile model-specific layer deferred to the live Anthropic docs (catalogued in its `references/live-model-docs.md`) rather than reciting version-specific behavior that goes stale. It disambiguates against the built-in `claude-api` reference (API/SDK mechanics — model IDs, pricing, parameters, tool-use schemas, caching) in its `description`; keep that boundary intact when editing either. The former Python-craft singletons (python-code-style, python-design-patterns, python-performance-optimization, python-testing-patterns) and debugging-strategies were removed: each was ~250–350 words restating PEP 8, ruff defaults, and standard debugging practice that a capable agent already applies unprompted. **Do not re-add generic coding-craft skills.** The bar for this directory is material the model does not already default to.
- `skills/test-prep/` contains standardized-test preparation skills — the `ielts-*` family and the `gre-*` family — including `ielts-progress-reporter`, which aggregates a practice vault's marked `feedback/*.md` files into periodic progress reports (band trends, recurring errors, revision gains) rather than marking individual drafts. The IELTS scoring skills each carry their own `references/ielts-band-descriptors.md` scoped to that skill (`ielts-writing-task1`, `ielts-writing-task2`, `ielts-speaking-coach`, `ielts-learning-planner`, and `ielts-grammar-coach`); there is no shared band-descriptor file. `ielts-grammar-coach` is IELTS-first (its band-descriptor file is scoped to the **Grammatical Range & Accuracy** criterion only): it estimates a **GRA band**, then diagnoses and drills the specific recurring errors holding it down via coded corrective feedback (mark the error + type, force self-correction) rather than silent rewrite, Vietnamese-L1 contrastive diagnosis, a persistent `error-ledger.yaml` of systematic errors with spaced re-probes, and targeted drills (interactive by default, with a two-file offline set as an option); it also has a general-English mode (no band). Keep the boundary clear — `ielts-writing-task1/2` and `ielts-speaking-coach` score the WHOLE task across all four criteria, whereas `ielts-grammar-coach` isolates GRA and drills recurring errors; and `ielts-progress-reporter` aggregates a vault into a report rather than marking or coaching. The `gre-*` family covers the shortened (post-Sept-2023) GRE with the same pick-one structure: `gre-verbal-reasoning` (Text Completion + Sentence Equivalence — predict-then-match, trap taxonomy, miss classification), `gre-reading-comprehension` (passages + paragraph-argument critical reasoning — passage mapping, wrong-answer taxonomy, line-reference discipline), `gre-quant-coach` (quantitative-comparison tactics, careless-error mechanism logs, content-gap triage; GRE test math only — research-level math routes to `professor-mentor-technical-teaching`/`theory-*`), `gre-issue-essay` (the sole AW task, scored 0–6 against its own `references/awa-scoring-rubric.md`, keyed to the six instruction stems), `gre-vocabulary-builder` (meaning clusters, charge, secondary meanings, spaced cloze re-probes; receives vocab-gap handoffs from `gre-verbal-reasoning`'s error log), and `gre-learning-planner` (allocation + daily vocab pipeline + POWERPREP milestones + test-date scheduling against application deadlines, with GRE-optional policies/percentiles/fees marked verify-live per the volatility rule). Keep the intra-family boundaries: blank-based items → `gre-verbal-reasoning`, passage-based → `gre-reading-comprehension`, word learning → `gre-vocabulary-builder`, scheduling → `gre-learning-planner`; and the cross-family boundary: GRE skills never handle IELTS tasks or vice versa (different tests, rubrics, and question logic).
- `skills/init-workspace/` is the top-level entrypoint for scaffolding non-coding, note-centric Obsidian workspaces: learning, ongoing research notes, research writing, academic applications, talks, test preparation, theory, and similar knowledge work. It must not claim generic software repositories, software applications, experiment codebases, websites, or other source-code projects. It asks one short intake batch (what the work is and what "done" means, project title plus an explicitly confirmed target directory, and what differs from the typical case); the user's answer confirms the target, so do not add a second confirmation round. It then chooses one of three paths: **use as-is** one of eight templates under `templates/<type>/` (seven heavy, plus the deliberately minimal `study-notes`); **adapt** the closest template, preserving its behavioral guarantees while updating Layout, routing, type labels, and all path-specific Operating-contract prose together; or **synthesize a lean bespoke vault** when none fits. Bespoke mode remains within the same non-coding, note-centric scope and always writes a folder tree plus `AGENTS.md`, while `references/` and `_dashboard/` are conditional on the intake. All paths write only into the target vault — never into the repo's `templates/` — and merge without overwriting on re-run. Templates: `ielts`, `paper`, `phd-application`, `research-notebook`, `study-notes`, `talk`, `theory`, `learn-a-topic`. `research-notebook` is for ongoing research thought without a single paper or learning curriculum: `questions/`, `ideas/`, `reading/`, `evidence/`, `decisions/`, `syntheses/`, and `log/` (dated meeting notes and weekly reviews together); small captures skip the pipeline, while substantial syntheses use it. **Templates are deliberately trimmed to folders that hold a distinct object type with its own lifecycle** — a folder that merely splits one object across two places is a decision the user pays at every capture, not organization. Do not re-add `inbox/` (the note method keeps the rough version inside the durable note under `## Raw capture`, so a staging folder is redundant), a separate `notes/` mirroring `learn-a-topic`'s `sources/` (bib info and reading notes belong in one file), `meetings/`+`reviews/` as separate folders (both are dated log entries), `paper`'s `data/` (it held pointers only — now `experiments/data-pointers.md`), or `talk`'s `assets/` (merged into `figures/`). Content-folder counts after the trim: `study-notes` 2, `learn-a-topic` 3, `talk` 3, `ielts` 3, `theory` 5, `paper` 6, `phd-application` 6, `research-notebook` 7. `study-notes` is the **leanest template and must stay that way**: exactly `notes/` + `exercises/`, one level deep, no `references/`, no `_dashboard/`, no `agents/` — its `AGENTS.md` inlines the whole capture → expand → store → query method precisely so the vault never grows a third folder. Its loop is one session → one note → one paired exercise file (`{YYYY-MM-DD}-{topic}.md` and `{YYYY-MM-DD}-{topic}-ex.md`), with the user capturing, the agent expanding, the user reviewing every expansion before it is saved, and the user solving the exercises (an agent never fills `# Solutions`). The date prefix and `-ex` suffix are the one sanctioned exception to metadata-lives-in-frontmatter, since they carry ordering and pairing. Route **by session** work here and **by source/subtopic** work to `learn-a-topic`. The `ielts` template ships AGENTS.md + dashboard only because installed `ielts-*` skills carry the band descriptors and feedback aggregation, and `study-notes` ships AGENTS.md only to protect its two-folder guarantee; the other six seed references. Each `AGENTS.md` opens with an agent-portable `## Operating contract`. Adapted contracts preserve the applicable invariants (non-coding knowledge work, source grounding or non-fabrication, marked uncertainty, faithful reporting and input checks where present, and the one-file pipeline rules where present) but must update type- and folder-specific wording so the contract matches the adapted Layout. A bespoke contract includes non-coding note work, non-fabrication, source grounding and uncertainty where claims are involved, report-faithfully behavior, and input preconditions. The seven skill-routing templates (`paper`, `theory`, `learn-a-topic`, `research-notebook`, `study-notes`, `talk`, `phd-application`) carry the input-precondition and report-faithfully rules; `ielts` (marking-only) carries neither. `talk` and `phd-application` additionally require grounding from the source rather than memory. `templates/_shared/agents/` holds **two** generalized, agent-portable protocols, a matched pair split by artifact size. `pipeline.md` is the research pipeline: **evidence → draft → review → verify** inside one artifact file, with a size gate and no per-stage side files. `note-method.md` covers everything below that gate — the everyday note loop **capture → expand → store → query**, so a template's "small notes skip the pipeline" no longer means "no method." Its load-bearing rules: the **raw capture is preserved inside the note** (never deleted once the prose reads well — it is the better expansion input, the hallucination fallback, and the record of what the user actually thought); an agent expansion is **reviewed by the user**, never accepted as written; frontmatter and section headers are a **retrieval contract** (renaming a header breaks queries that chunk on it); and **querying the vault is not retrieval practice** — delegating retrieval to an LLM delegates the learning benefit, so a query locates what to re-derive rather than substituting for recall. Its claims about note-taking research are **epistemically flagged** per `DESIGN-PHILOSOPHY.md` — structured-beats-unstructured is *supported* (and is an overall achievement difference, **not** a retention-rate effect: the source trial's time×group interaction was non-significant), LLM expansion is *efficiency-only* with retention never measured, and the "digital feels easy so it must be shallow" cognitive-load story is *contested* by the same study's own regression. Do not promote any of these to a stronger claim. Copy **both** files into `<vault>/agents/` for `paper`, `theory`, `learn-a-topic`, `research-notebook`, and substantial bespoke source-grounded synthesis/research vaults; lighter or non-research vaults get no `agents/` folder. Every vault gets a one-line `CLAUDE.md` containing `@AGENTS.md`. Every `AGENTS.md` ends with synchronized Obsidian formatting rules: keep each prose paragraph or list item on one physical line and rely on Obsidian soft wrapping; require valid YAML frontmatter from line 1 and quoted wikilink lists in frontmatter; and forbid raw `|` in table cells. Keep this block synchronized across all eight templates.
- `templates/skill-template/` is for reusable starter material when creating new skills.
- `experiments/` is for shell scripts or prompt variants used to test skill behavior.
- `results/` is for saved evaluations or notes about which skill behavior worked.

Recommended skill layout:

```text
skills/<category>/<skill-name>/
├── SKILL.md
├── examples/    # optional calibration examples
├── evals/       # optional test prompts or evaluation metadata
└── scripts/     # optional helpers the skill actually uses
```

## Skill taxonomy

The category directory names *are* the taxonomy — there is no second list to keep
in sync. A new skill goes in exactly one of these:

| Directory | Scope |
|---|---|
| `research-discovery` | framing, positioning, gap-finding, novelty checks |
| `research-evidence` | literature mapping, Related Work, surveys, citation verification |
| `research-reasoning` | theorems, claims, proofs, derivations, formal audits |
| `research-experimentation` | experiment/ablation design, baselines, statistics, evaluation, run diagnostics |
| `research-engineering` | implementation recipes, codebase structure, reproducing a paper |
| `research-communication` | paper sections, figures, argument spine, talk planning |
| `research-publishing` | review, rebuttal, venue targeting, reproducibility, artifact release |
| `research-workflows` | the `flow-*` orchestrators that sequence the singletons |
| `learning-and-metacognition` | teaching, exercises, teach-back, co-solving, critique, knowledge-debt |
| `academic-career` | the `apply-*` family: profile, CV, SOP, fit, recommenders, outreach |

## Skill authoring conventions

- After adding, editing (renaming/moving/re-describing), or removing any skill, update all three registries so they stay in sync: this `CLAUDE.md` (structure/disambiguation notes), `README.md` (the skill catalog), and `skills.json` (the machine-readable index — keep its `name`, `path`, `category`, and `description` correct, and verify it still parses as valid JSON).
- If the change introduces or revises a durable design principle, evidence-backed learning protocol, or cross-skill role boundary, update `DESIGN-PHILOSOPHY.md` as well. Keep operational skill instructions in `SKILL.md`; keep the philosophy file focused on rationale and references.
- Keep one skill focused on one clear capability.
- Keep each skill self-contained: a skill must not depend on resources outside its own directory, and skills must not share files or link into each other (e.g. no `../references/…` cross-references). When several skills need the same reference material, give each its own copy scoped to that skill rather than pointing them at a shared directory.
- Put activation guidance in the frontmatter `description`; agents use this to decide when to load the skill. Do not use a separate `when_to_use` frontmatter key — it is not read by agents. Merge all triggering guidance into `description`.
- Make descriptions specific and slightly pushy about when to use the skill, including common user phrasings.
- Group tight "pick-one" skill families with a short, domain-derived name prefix so siblings sort together and read as one suite: `apply-*` (PhD/career applications), `flow-*` (orchestrators/routers), `deck-*` (slide/deck builders), `theory-*` (theory-heavy math/ML tools), plus the existing `ielts-*`, `python-*`, and `banking-*`. Do not prefix the broad research singletons — their directory already conveys the category, and prefixing all of them adds churn without aiding triggering (agents match on `description`, not name).
- Prefer procedural guidance: when to use the skill, when not to use it, the process to follow, and the expected output format.
- When two skills overlap, disambiguate in the frontmatter description and body. For example, field mapping belongs to `literature-triangulation`, polished Related Work prose inside an original paper belongs to `related-work-writer`, and standalone survey/tutorial/perspective papers belong to `survey-paper-writer`.
- Add `examples/` only when examples materially improve calibration.
- Add `scripts/` only when repeated manual work justifies a helper script.
- Add `evals/evals.json` for new skills when realistic test prompts will help evaluate triggering or output quality.
- Avoid broad scaffolding until there is real content for it.
- Remove low-priority or redundant skills instead of archiving them, unless they support the user's research, PhD application, or coding workflows.
- Do not vendor a `skill-creator` skill into this repo. Creating, editing, and evaluating skills uses Claude Code's built-in skill-creator, which ships the full eval/benchmark tooling; a repo-local clone only duplicates the `name`, shadows the built-in, and goes stale (a prior clone carried only `SKILL.md` while referencing scripts/agents/references it did not include).

## Commands

There is no build system, linter, test runner, or `package.json` in this
repository — skills are consumed directly from git by the `skills` CLI, which
needs only `skills/` and `skills.json`. Installation wrappers live in
`scripts/install.sh` / `install.ps1`.

After any skill add / edit / move / removal, run these checks:

```bash
git status

# 1. Frontmatter must PARSE AS YAML, not merely look right.
#    A plain scalar containing ": " is invalid and the skills CLI drops the
#    skill SILENTLY — no error, it just vanishes from the listing. Use `>-`
#    block style for any description containing quotes, colons, or examples.
python3 -c '
import os,re,yaml
for r,_,fs in os.walk("skills"):
    if "SKILL.md" not in fs: continue
    m=re.match(r"^---\n(.*?)\n---",open(os.path.join(r,"SKILL.md")).read(),re.S)
    fm=yaml.safe_load(m.group(1))
    assert fm["name"]==os.path.basename(r), r'

# 2. Registries must agree: skills.json <-> disk <-> README catalog, all 3 equal.
# 3. Depth: no SKILL.md more than two levels under skills/ (see Structure above).
```

The authoritative end-to-end check is the CLI itself, which catches what static
checks miss. Against a local clone of the working tree:

```bash
npx skills add "file:///path/to/clone" -l    # must list EVERY skill, no flags
```

If executable helper scripts are added under `experiments/` or skill-local
`scripts/`, document the exact run commands here when they become stable.
